# ANTLR 4.13.2.19

1 November 2026

This is a line-number release of the optimized fork. It follows 4.13.2.18 (`b882368de901d62590d7196c1d5e2b4ff50266a7`). Maven coordinates are `me.sunlan:antlr4:4.13.2.19`, `me.sunlan:antlr4-runtime:4.13.2.19`, `me.sunlan:antlr4-maven-plugin:4.13.2.19`, and `me.sunlan:antlr4-annotations:4.13.2.19`. The Java runtime and the tool target JDK 8. HPPC remains an implementation detail and does not appear on any public or protected API.

Grammars do not need to be regenerated. Existing generated lexers call `LexerATNSimulator.consume`, and that is the method that changed. The precedence LL(1) table and the ASCII lexer edge arrays are unchanged.

## Compatibility

A bare carriage return is now a line ending. Token line and column after a classic Mac CR move. CR+LF does not.

* A line feed increments the line and sets the column to 0. That is unchanged.
* A carriage return that is not followed by a line feed does the same. Carriage return at end of input is that case.
* The carriage return of a CR+LF pair only increments the column. The following line feed is the one line break. Columns around CR+LF stay as they were in 4.13.2.18.
* Two bare carriage returns are two breaks. A carriage return after a line feed is another break.
* `Lexer.recover(RecognitionException)` consumes through the same method, so a bare CR skipped during recovery advances the line the same way.

`consume(CharStream)` documents this rule. The DFA walk calls `consume(CharStream, int)` and passes the code point it already loaded. That overload calls `LA(2)` only when the code point is a carriage return. `LA(2)` is end of file when the CR is the last character, including on `UnbufferedCharStream`.

This is the fix suggested for [GROOVY-12435](https://issues.apache.org/jira/browse/GROOVY-12435) on [apache/groovy#3070](https://github.com/apache/groovy/pull/3070). A source file that uses CR by itself keeps later tokens, syntax errors, and EOF on the following line.

## Runtime

`DiagnosticErrorListener` reports the alternatives in an ambiguity through `PredictionMode.getAlts`. The reported set is the same. `RuleDependencyChecker` still groups dependencies by recognizer and still checks every class in the batch before it marks any of them done. `ArrayEdgeMap.put` still returns the same map. `putAll` still copies only occupied slots, and a hole in the source still leaves a destination edge in place.

## Performance

There is no throughput change to claim against 4.13.2.18.

The warm lexer loop is still `LexerATNSimulator.execATN`. The warm parser return is still `tryLL1Prediction`, `tryPrecedenceLL1`, or `execDFA`. The new `LA(2)` runs only for CR, so identifiers, operators, spaces, and line feeds do not take it. The 24 October flame graph still describes that steady state: `execATN` at 25.4% self time and `adaptivePredict` at 17.1%. Widening `execATN`, or reserving one token slot per code point, lost lexer cells on that gate and stays out. Pair ratios on this host swing from about 0.93 to 1.08. A parser-only edit cannot move lexer reuse, and lexer reuse does not call `adaptivePredict`.

The write-up is `doc/perf-reports/performance-verification-report-no-hot-path-round-vs-b882368de-20261101.md`. The flame graph is `doc/perf-reports/flame-serial-two-stage-20261024.html`.

Groovy's generated lexer does not override `nextToken`. Its largest parser rule method, `expression`, is 6,915 bytes, under HotSpot's 8,000-byte cutoff. No generated Groovy lexer or parser method in that build is at or over the cutoff.

## Tests

On JDK 8, the runtime suite ran 1,203 tests and the tool suite ran 1,619 tests. Both reported 0 failures. The tool suite skipped 14 tests. One of those skips is `TestPerformance.compileJdk` when `JDK_SOURCE_ROOT` is unset.

The new tests lock bare CR, CR at EOF, CR+CR, LF followed by CR, and CR+LF, through the direct consume path, a warm and cold DFA walk, token line and column, and `Lexer.recover`. A one-code-point `UnbufferedCharStream` checks that `LA(2)` reads the next character before the CR is consumed. The tool expectation for `"34\r 34 a2 abc \n   "` now places the tokens after the bare CR on line 2 and EOF on line 3. CR+LF expectations are unchanged.
